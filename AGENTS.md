# Maintaining agensia-plugins

This repository is the canonical distributable source. Read `README.md` and `docs/PORTABILITY.md`, then the affected plugin README and skill before editing. Follow the enclosing workspace’s rules when available. Do not copy private business memory into this repository.

- Use relative paths with an explicit base: skill resources relative to their skill directory; business files relative to the selected workspace; shell examples relative to their documented working directory. Do not hardcode personal directories, cloud accounts or sandbox mounts.
- Follow the Agent Skills standard: `SKILL.md`, YAML name matching the containing directory (lowercase hyphens, at most 64 characters), concise description of capability and trigger (at most 1024 characters), string-valued metadata, and linked resources for detailed procedures. Keep entrypoints below 500 lines. The repository applies stricter Windows budgets: skill names at most 40 characters, filenames at most 60 UTF-16 units, relative file paths at most 140 UTF-16 units, and full paths at most 259 units including the checkout location. Preserve former identifiers in the migration maps when shortening names.
- Each child plugin also has an Agent Plugins v1 `plugin.json` at its own root. Keep its shared metadata/version aligned with `.claude-plugin/plugin.json`; retain native adapters separately. Put portable MCP declarations only in that child package's `mcp.json` with the matching schema. Validate and export with `scripts/skill_bundle.py`; do not imply host installation or runtime certification.
- The repository-root `plugin.yaml` and `__init__.py` are the native Hermes Git-install adapter. Register canonical top-level skill directories in place; do not duplicate skills, register nested helpers separately, add tools/hooks/MCP servers or write host configuration through this adapter. Validate root discovery and registration separately from child portable manifests, and document only checks actually run.
- Preserve workflow safeguards, existing authorization and user intent. Do not infer tool access from instructions. Keep host-specific adapters separate from reusable instructions. No silent external sends, publication, credential copying or fabricated tool results.
- Never read, enumerate, copy or export `.secret/`. Exclude runtime state, private local configuration and credentials from packages.
- Preserve third-party licences and attribution. Record local adaptations and name changes. Do not overwrite local additions with a destructive upstream mirror sync.
- **Every skill or skill-resource change must update both its plugin README and the repository README in the same change.** Update intended departments in skill metadata and `docs/departments.json`; regenerate the catalog with `python3 scripts/skill_bundle.py docs`. Include a human-readable explanation of behavior changes in the plugin README. The fingerprint catches resource-only changes too.
- Thinking-framework sections in `SKILL.md` and `references/thinking-frameworks.md` files are generated. Edit `docs/thinking-frameworks/frameworks.json` or `skill-map.json`, then run `python3 scripts/thinking_frameworks.py`. Map a skill only when a framework fits one of its actual steps. Frameworks never relax a skill's evidence, authorization or approval rules.
- Keep the README department diagram consistent with the department mapping. Maintain this department diagram directly as fenced Mermaid in Markdown, as requested by the user for compatibility. No draw.io tool or service is required for this diagram. Keep the README preview and `docs/department-map.md` in sync. Department labels are intended users, not an assertion of actual deployment.
- Run `python3 scripts/skill_bundle.py validate` before handing off work. In a Git checkout with a HEAD commit, also use `--base HEAD` for uncommitted changes; compare committed branches against their actual base revision. Run meaningful tests for changed scripts and packaging. Do not claim cross-platform runtime testing from format checks alone.
- GitHub pushes, publishing and host installation are separate actions. Respect the user’s chosen manual release process.

Business source paths are semantic examples. Never require the author’s workspace taxonomy. Resolve actual inputs and output destinations with the recipient. Keep README explanations concise and include Mermaid diagrams. Update both collection manifests, catalogs and migration records when moving a plugin.

- Never commit or push ZIP archives into repository files. Build them under ignored `dist/` and distribute them only as GitHub Release assets. Installation links must use Releases. Do not rewrite existing Git history without explicit authorization.
