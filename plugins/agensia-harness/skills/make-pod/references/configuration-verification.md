# Configuration verification and score-guided improvement

Use this guide when revising Pod outcomes, ontology, Talents, hierarchy or their Workflow bindings. These are generic checks derived from configuration exercises, not a guarantee that every platform build behaves identically. Record the target environment, visible version/build when available, role, date and exact object revision. Keep private case evidence in the selected workspace, outside this distributable skill.

## 1. Keep evidence layers separate

| Layer | What establishes it | What does not |
|---|---|---|
| Intended design | Versioned requirements and source-to-output mapping | A generated suggestion |
| Saved configuration | Reopened fields, source associations and selected role match the intended revision | Visible edits, a save click or a success toast alone |
| Source retrieval | Actual content and locators returned by an authorised reader | Attachment names or a Pod badge |
| Runtime execution | Current task result, tool evidence and resulting state | Published/Approved status or a high configuration score |
| Human decision | Actual assigned-human decision bound to case, revision and reviewed artifact | Setup approval, silence or generated acceptance text |
| Useful outcome | Executed acceptance cases and owner-defined result | A fluent answer or an unrun golden specification |

Never promote evidence from one layer into another. A missing prerequisite blocks its dependent claim or action; continue independent authorised work.

## 2. Commit, save, reopen and compare

1. Inspect the existing object, revision and status. Reuse its editable draft or supported revision route; preserve the accepted baseline.
2. Capture the intended field payload and source inventory before editing. Match sources by filename plus version/provenance, not display order alone.
3. Edit one logical stage. Use the stage's supported commit/advance action, such as **Next**, where required. Switching tabs or calculating a score may not commit form state.
4. Save, wait for completion, reopen the exact saved revision, and compare fields with the intended payload. Check semantic text, exact source references and counts; normalise only harmless whitespace.
5. Compare outcomes, ontology descriptions, attached source versions, Talent Name/Description/Operation, selected hierarchy and each role message. A correct name does not prove its Operation or message persisted.
6. After any regeneration, inspect for appended or overlapping Talents, extra roles, renamed references, changed authority or a newly selected hierarchy. Reconcile against the approved design rather than enforcing an arbitrary count. Commit removals and edits through the same readback loop.
7. Recheck affected Workflow task bindings separately. A Pod source change does not prove that task-level source/template associations or role selection changed with it.

If displayed and reopened values differ, record a persistence defect and fix the form state before scoring or submission. A whitespace edit may trigger validation in a particular build; it is not a substantive quality improvement or reliable general fix. Do not report persistence until readback agrees. Capture evidence before and after the repair.

## 3. Use the page assistant as an adviser

When available and authorised, ask the helper to explain the current page, component relationships and remaining gaps. Request the exact object/revision it sees and whether its answer comes from current fields, evaluator feedback, document reads or inference.

- Separate **evaluator feedback**, **helper inference**, **saved UI evidence** and **runtime evidence** in the change log.
- A helper may receive stale or mixed snapshots. Verify surprising claims against the reopened object; a helper's assertion of tool access or saved backend state is not proof.
- Request concise, concrete changes with affected fields, source sections and intended acceptance checks. Apply only changes supported by evidence and existing authority.
- If a section exposes no score, report it as unscored and review it with explicit checks. Do not invent a Talent or hierarchy score from another section's rating.
- Record scores and written gaps as separate observations. An empty or hidden gap panel does not establish that no gaps exist.

## 4. Improve substance, not the score display

Use the target build's actual scoring dimensions and rubric where exposed. For Completeness/Uniqueness/Usability, maintain one row per scored section: committed revision, source versions, score, exact feedback, proposed cause, change and re-evaluation result. Preserve regressions as well as gains; do not cherry-pick the best run.

Recalculate after a meaningful, committed change. If feedback cites superseded references, verify saved state before changing the content again. Scores may vary; configuration scores are not paired runtime benchmark results and do not establish enforcement or go-live readiness. Never promise an exact maximum score or keep resubmitting unchanged content until a favourable score appears.

Use a promise-to-source matrix to distinguish reusable procedure from required case input. Methods define how to work; deployment bindings define where and under whose authority; case records supply facts; runtime receipts prove actions. Synthetic examples test shape and failure handling but never substantiate real customer findings, sample counts, capabilities or decisions.

If feedback requires missing case evidence, first look for suitable evidence in the authorised source scope. If none is available, identify the smallest necessary evidence pack and its owner. Public source material may support public claims; private interviews, tests or approvals cannot be invented. Do not mislabel authored methods as proprietary, externally validated or certified to improve uniqueness. Do not weaken an agreed outcome merely to improve a score. Record the unmet target and continue independent work.

## 5. Keep sources and instructions consistent

- Give each outcome a distinct purpose, input contract, procedure, decision rules, output schema, examples and acceptance checks. Share genuinely common controls with explicit applicability.
- Remove ambiguity and obsolete associations, not required knowledge. A larger upload count is not proof of coverage; consolidation is useful only when all needed content remains traceable.
- Match outcome promises, source filenames, section IDs, versions, Talent instructions, role messages and Workflow bindings. Update consumers when replacing a source and retain historical evidence outside the active upload set.
- Define terminology once. Keep provenance separate from evidence status; make every required field appear in the actual output template, including source/version/date/locator where required.
- Make examples obey the same rules as the procedure: consistent labels, denominators, duplicate handling, conflict treatment and exclusion results. Define categorical result values and missing-input behaviour.
- Keep facts, vendor statements, observations, hypotheses and synthetic material distinguishable. Attach primary method sources where needed; a citation or certification claim must not exceed the source's scope.

## 6. Validate one bounded runtime path

After configuration readback passes and execution is authorised for verified non-production targets, test one bounded path: read actual sources, produce the current task output, reach the genuine human checkpoint, save through an available tool, reread the artifact and verify any separately authorised write. Stop at the boundary of the authorised test; do not manufacture a human decision to continue.

Investigate task dispatch separately from source availability. A task that answers the launch request or starts another process has not completed its assigned work. A prompt reminding it to execute only the current task is a mitigation, not proof of tool isolation. Preserve run/task evidence, diagnose the available bindings and tools, and retest before broader rollout. Do not infer a second run or backend cause from assistant text alone.

## 7. Regression candidates and handoff

Seed applicable cases; mark each **unrun** until executed in the target environment:

| Case | Expected check |
|---|---|
| Edit then navigate/save/reopen | Exact intended fields persist; stale references are detected |
| Regenerate after ontology changes | No unintended duplicate capabilities, extra authority or hierarchy selection |
| Replace a source | Every dependent reference resolves to the intended current source |
| Missing or conflicting case input | Bounded gap output; no invented fact or synthetic substitution |
| Current task receives a launch request in context | Executes its assigned task without unsupported redispatch |
| Human checkpoint without a decision | No invented approval or dependent consequential action |
| Save or write acknowledgement | Independent readback verifies the actual artifact or record |

Handoff reports changed paths/objects, saved readback, scores, checks actually run, unrun tests, remaining evidence gaps and next owner. Keep design readiness, platform approval and runtime acceptance separate. Follow [Pod evaluation](pod-evaluation.md) for benchmark comparisons and [Workflow execution contract](workflow-execution-contract.md) for task controls.
